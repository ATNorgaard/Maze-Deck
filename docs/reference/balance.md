# Balance — what the simulator found

Generated by `npm run simulate` in `packages/rules` (1500 seeded runs per row,
4 seats at +3 across the board, Maze DC 15). Policies only read **face-up**
river cards, so these are numbers a real table could produce.

```
As written
  random play                through 100.0%  rounds 6.2  encounters 0.99  reserve  4.6
  competent play             through 100.0%  rounds 4.2  encounters 0.91  reserve  7.5

Without Forge a Path
  competent, no forge        through 100.0%  rounds 4.1  encounters 0.76  reserve  0.1

If a lost encounter ends the run (coin-flip combat)
  competent                  through  54.4%  rounds 3.6  encounters 0.90  reserve  5.9
  competent, no forge        through  63.5%  rounds 3.7  encounters 0.74  reserve  0.1

Difficulty dials, competent play
  target 3                   through 100.0%  rounds 2.7  encounters 0.51
  target 7                   through 100.0%  rounds 5.5  encounters 1.18
  +3 Monsters                through 100.0%  rounds 4.1  encounters 1.87
  Maze DC 18                 through 100.0%  rounds 4.3  encounters 0.92  reserve  4.2
  Maze DC 10                 through 100.0%  rounds 4.0  encounters 0.90  reserve 14.2
```

## 1. The card game cannot be lost

Every configuration gets through, because **the rules contain no loss
condition**. Two strikes hands the party to a combat encounter; winning removes
a Monster from the deck, and the source never says what losing does. The only
row that ever fails is the one where we invent a consequence — combat is a coin
flip and a loss ends the run.

This is very likely intentional: it is a travel subsystem inside a D&D session,
and D&D is where characters die. But it means **the app's real output is not
win/lose, it is how many times the party gets found** — 0.5 to 1.9 encounters a
run depending on the dials. Worth deciding explicitly whether the app should
have a loss state of its own at all.

## 2. Maze DC is almost inert

DC 10 against DC 18 moves the run by 0.3 rounds and the encounter count by 0.02.
The Danish document sells the Maze DC as "single-point scaling" that tunes the
whole system — it does not, and the reason is structural: **you pick a card
whether or not your action succeeded**, so a failed check costs a turn's
optional benefit and nothing else. There is no failure penalty for the DC to
scale.

Where DC does show up is `reserve` — 14.2 cards at DC 10 versus 4.2 at DC 18 —
which is just Forge a Path landing more often.

The dial that actually works is **the deck**: `+3 Monsters` doubles the
encounter rate, and the escape target sets the length. Raising the DC is close
to a no-op.

## 3. Forge a Path does not pay for itself

With it: 4.2 rounds. Without it: 4.1. It adds an average of 7.5 Clear Paths to a
23-card deck and changes nothing, because a run lasts about 16 turns and the
cards it adds arrive in the discard — often after the run is already over.
"Deck dilution" is a real mechanic on paper that a four-round run never collects
on.

## 4. Five Clear Paths in a deck of five is not the constraint it looks like

The target is 5 and the deck holds exactly 5, which reads as razor-thin. It is
not: the river shows 3 at a time, unpicked cards stay, the discard reshuffles,
and roughly 16 picks happen. Every Clear Path comes around. Even a target of 7
never fails.

## Options, if any of this should change

None of these are needed for the app to work — the engine implements the rules
as written. They are for the game.

- **Give a failed action a cost.** The cleanest fix for the inert DC: a failed
  check means no action *and* the card is drawn blind, or the turn passes with
  no pick.
- **Let strikes persist across encounters**, or make the third strike something
  worse. Right now surviving is a full reset.
- **Speed Forge a Path up** — new Clear Paths to the top of the deck rather than
  the discard — or drop it and give STR the obstacle-clearing job, which is
  what the prototype had quietly done all along.
- **Leave it exactly as is** and treat the encounter count as the output. This
  is a defensible reading: the subsystem's job is to generate two or three good
  scenes and one fight, not to be won.

```bash
cd packages/rules && npm run simulate -- 2000
```
